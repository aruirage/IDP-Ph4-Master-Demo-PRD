## 确认页与回写

### 1. 请 API 把结果整理成确认页可以直接用的结构

请客户在 API 内部把不同场景和字段整理好，给 IDP 一套清晰、稳定的确认页结构。这样后续即使客户调整内部场景、规则或字段，IDP 也能沿用同一套确认、回写和展示逻辑。如果现有数据结构还不清楚，可否由 IDP 定义返回结构并提供 JSON 样例，请你们确认后按该结构返回？

| API 返回内容 | IDP 怎么用 |
|---|---|
| 照合项 ID（`itemId`） | 标识这条照合结果。 |
| 照合字段 ID（字段名及返回位置待定） | 会上提出用字段级 ID 关联修改前后的同一个字段。用于按字段重新照合时标识被修改的字段。请客户确认字段名、返回位置，以及重照合前后是否沿用同一个字段 ID。 |
| 是否人工确认（`needsReview`，布尔值） | `true` 送人工确认，`false` 跳过人工确认。 |
| 是否回写（`shouldWriteBack`，布尔值） | `true` 时，按 API 返回的采用值和目标位置回写。需人工确认的先等确认完成。`false` 时保留原值。 |
| 主数据下拉列表（`masterDataMatches`） | 每项返回 `type`、`label`、`value`，以及置信度和主要素标记。`type` 只用 `recommended` 或 `candidate`。空列表时隐藏下拉，字段保留 OCR 原值。 |
| 置信度（`masterDataMatches[].confidence`） | 在对应的下拉选项上显示，由 API 返回。 |
| 是否主要素（`masterDataMatches[].primary`，布尔值） | 拆分时由 API 为各选项标记。`true` 表示主要素，`false` 表示追加要素。IDP 按标记显示标签。 |
| 确认原因（`reviewReason`） | 有内容就显示在确认原因处。 |
| 其他信息（`remarks`） | 每项返回 `label` 和 `value`。建议名称、判断依据和备注都在输入框下方展示。 |

以下示例把主要素和追加要素各自的推荐与候选放在同一个 `masterDataMatches` 列表中。

```json
{
  "itemId": "I1",
  "source": {"type": "FIELD", "documentId": "D1", "fieldName": "傷病名1", "fieldIndex": 0},
  "needsReview": true,
  "shouldWriteBack": true,
  "masterDataMatches": [
    {"type": "recommended", "label": "マスタ推奨", "value": "1型糖尿病", "confidence": 90, "primary": true},
    {"type": "candidate", "label": "マスタ候補", "value": "2型糖尿病", "confidence": 88, "primary": true},
    {"type": "recommended", "label": "マスタ推奨", "value": "糖尿病性腎症", "confidence": 86, "primary": false},
    {"type": "candidate", "label": "マスタ候補", "value": "糖尿病性腎障害", "confidence": 82, "primary": false}
  ],
  "reviewReason": "匹配到多条主数据，需人工确认",
  "remarks": [{"label": "照合依据", "value": "OCR 识别值为「糖尿病」，未注明分型"},{"label": "名称提案", "value": "急性腹症"},{"label": "确认备注", "value": "因为XX, 所以XX"}]
}
```

未找到可选主数据但仍需人工确认时，列表返回空数组。页面保留 OCR 原值、隐藏下拉，展示原因和建议名称。

```json
{
  "itemId": "I2",
  "source": {"type": "FIELD", "documentId": "D1", "fieldName": "傷病名1", "fieldIndex": 0},
  "needsReview": true,
  "shouldWriteBack": false,
  "masterDataMatches": [],
  "reviewReason": "未找到可采用的主数据",
  "remarks": [{"label": "建议名称", "value": "自己炎症症候群"}]
}
```

#### 拆分结果示例

主要素和追加要素的照合结果能否放进同一个下拉，供操作员选择？选中追加要素后怎么回写？

```json
{
  "masterDataMatches": [
    {"type": "recommended", "label": "マスタ推奨", "value": "1型糖尿病", "confidence": 90, "primary": true},
    {"type": "candidate", "label": "マスタ候補", "value": "2型糖尿病", "confidence": 88, "primary": true},
    {"type": "candidate", "label": "マスタ候補", "value": "糖尿病性腎症", "confidence": 82, "primary": false}
  ]
}
```

是否人工确认和是否回写分别返回。如果要求回写，请同时提供可采用的值和对应位置。候选可以改选时，请说明选中某一项后，应使用该项的哪些值和位置。

**请客户给一个异常响应样例**　如果照合没跑出结果，但项目仍需人工确认，请给出同一结构的响应，标出受影响项目和 `needsReview=true`。没有可选候选时，请确认操作员能否保留 OCR 原值并完成确认。

［C-01、§4.2、§5.3、§5.7、§8.4］

#### 会议结论

确认页使用固定结构。下拉只有「主数据推荐／主数据候选」两种类型，并显示置信度。确认理由独立显示，照合依据、确认备注、建议名称等统一放入 `remarks`，有内容才显示。写回由 API 返回的字段控制，允许写回时用最终采用值覆盖原值。是否人工确认仍以统一字段分流，正式响应契约等新版式样书。

v1.2 已规定主要素和追加要素的选项统一放入 `masterDataMatches`，通过 `primary` 标记，且每个选项返回对应的主数据行和 `targets`。原先要求客户补充追加要素回写样例，已由 v1.2 §5.10、§8.4 覆盖。

## 调用范围与工作流

### 2. Fallback 本期能否先关闭，放到下一期？

如果本期必须支持，请用一个同时有已配置和未配置帳票的案件，给我们一组实际请求和最终响应。请指出未配置帳票里哪些字段或表格行被拿去照合、跟哪张主数据表比、结果对应原帳票的哪里。如果没有识别出任何可照合字段，也请说明会返回什么。［§4.1］

#### 会议结论

Fallback 放到下一期。本期关闭，按已配置的照合组处理。

### 3. 一个案件分两批来，要怎么送给 API？

用同一个案件举例。第一批是申请书和诊断书，第二批才收到收据。三张加起来没有超过单次请求上限。

**走法 A　等资料齐了，一起送**

```text
第一批：申请书、诊断书 → 先等
                           ↓
第二批：收据           → 三张齐了 → 一起提交 → Task 1 完成 → IDP 拿整案结果
```

**走法 B　第一批先送，后来再收到第二批**

```text
第一批：申请书、诊断书 → 先提交两张 → Task 1 处理中或已经完成
                                          ↓
第二批：收据到了       → 只送收据？还是三张一起重送？
                                          ↓
                         第二次提交 → Task 2 → 哪次结果覆盖整案？
```

**会前对照图的问题：**

1. 你们的 API 要我们等三张齐了再送，还是第一批可以先送？
2. 如果可以先送，收据来了以后，第二次只送收据，还是重送三张？请在图上标一下，IDP 要等哪一个或哪几个 Task 的结果，才能进工作流下一步。

式样书已经写了怎么查询 Task 结果，但没有说明案件什么时候算“最后一批”或“资料收齐”。**Task 完成只能说明这次提交跑完，不能证明不会再有新资料。** 如果走“等资料齐了再提交”，IDP 需要在自己的收件流程里确定什么时候算齐件。［§4.1–4.4、§4.15、§8.3–8.4］

#### 会议结论

v1.2 已明确：标准化 API 不处理批次状态或最后一批到达标记；IDP 在案件单据齐全后整案提交。后续追加、替换、删除或重新处理单据导致输入变化时，取消未结束任务并按最新资料整案重请求。案件最后一次请求的 Task 终止并反映结果后推进工作流。上游如何通知 IDP 案件资料齐全，属于 IDP 受理流程，不是该 API 提供的字段。

## 照合组配置

### 4. 同一个字段能否只配置到一个照合组？

**本期方案**　配置照合组时，同一个 OCR 字段只能加入一个组，用来读取、写回或读写都适用。例如「傷病名1」已在 A 组，B 组再选它时，提示这个字段已被 A 组使用，并禁止保存。

**请客户确认**　式样书允许多个组读取同一个字段。为简化人工确认和回写，本期能否在配置时就限制一个字段只能属于一个组？［S-04、§5.1］

**以下是会前讨论的例外，仅在之后要放开跨组限制时再确认：**

- **两个组都读取同一个字段。** 比如 A 组和 B 组都读取「傷病名1」，API 会按组生成各自的照合结果，每条有自己的 `groupId`、`itemId` 和 `needsReview`。如果两条都是 `true`，能否在同一个 OCR 字段下按组分别展示候选和原因，并分别确认？请客户给一份包含两条结果的响应样例。
- **两个组都要写回同一个字段。** 式样书规定后面的组会以 `WRITE_CONFLICT` 转人工。如果确实需要多个组读取同一个字段，请确认能否只允许一个组写回，以减少冲突处理和测试。［§2.8、§5.1、§5.3］

#### 会议结论

v1.2 已规定：同一单据项目或表格列只能放入一个组，设置校验会返回 `FIELD_IN_OTHER_GROUP`。案件标准字段可供多个组读取；同一案件标准字段作为回写目标时只能有一个组。原问题已由 §5.1、§4.9 覆盖。

## 标准变量与重新照合

### 5. 同一个标准变量有两个不同的值，怎么处理？

推荐流程为 OCR 抽出 → Data Mapping → 主数据照合 → OCR 抽出确认。IDP 在调用照合 API 时，通过 `caseResult` 传入标准变量。

**会上只确认**　例如申请书和诊断书上的「性别」映射到同一个标准变量，但识别值不同。IDP 应该按映射规则选一个值再传，还是要把两个来源值都传给 API？请用这个冲突例子给一份 `caseResult` 请求和对应响应，说明由谁决定采用哪个值，以及需要人工确认时 API 怎么返回。［§4.1、§5.2］

同一案件的输入举例。下面只展示冲突的来源，实际 `caseResult` 的格式等客户确认。

```json
{
  "caseNo": "C1",
  "documentValues": [
    {"documentId": "D1", "field": "性别", "value": "女"},
    {"documentId": "D2", "field": "性别", "value": "男"}
  ]
}
```

#### 会议结论

v1.2 已明确：把来源不一致的项目放入 `caseFieldConflicts`，不从来源中自行选值；API 将使用该标准字段的照合对象作为 `CASE_FIELD_CONFLICT` 返回，`needsReview=true`、不回写、无候选。操作人员修正标准字段后，按案件最新资料整案重新请求。请求和响应格式见 §4.1 示例及 §6。

### 6. 修改字段后，怎么按字段重新照合？

例如 5 号字段在确认页先改成 B，又改成 C。点击「重新照合」时，IDP 用哪个值发请求？

**请客户确认字段定位方式**　请求里用什么标识定位要重照合的字段？首次为空、没有生成照合项的字段，补填后也应能用同一套方式定位。［§4.6、§5.2］

#### 会议结论

操作员点击「重新照合」时，IDP 使用确认页编辑缓存中的最新值。v1.2 以 `fieldId` 关联重新标准化前后的项目；单字段或表格单元格修改只重新标准化当前 item，案件级输入变化则按案件整体重新请求。见 §4.6。

### 7. 两份逻辑文件都有编码栏，该写回哪一份？

同一案件 OCR 抽出后有三份逻辑文件。F1 是申请书，F2 和 F3 都是诊断书。照合组配置为「读申请书的伤病名，把照合得到的 ICD 编码写回诊断书」。F2 和 F3 都有 ICD 编码栏。

```text
F1 申请书 · 伤病名
        ↓ 主数据照合
API 得到一个 ICD 编码（例如 J18.9）
        ↓ 组配置要求写回诊断书的编码栏
        ├─ F2 诊断书 · ICD 编码栏
        └─ F3 诊断书 · ICD 编码栏
        → 目标位置不唯一，转人工确认
```

v1.2 已规定：无法确定唯一回写位置时，不回写到不确定的位置，不将该位置放入 `targets`，并以 `AMBIGUOUS_SOURCE` 标记需确认。具体让操作员选择哪个逻辑文件以及如何把配置的多个主数据值分配到目标字段，由 IDP 设计。［§5.2、§5.7、§5.10］

**IDP 设计方案**　目标位置明确时按既有配置直接回写，不增加人工选择。只有同一照合结果对应多个可能的写入来源、系统无法确定写入哪份逻辑文件时，才在确认页让操作员选择目标文件，再按选择结果分配回写。多个主数据返回值与字段的映射由 IDP 配置设计。

#### 会议结论

需要支持配置主数据返回的多个值分别写入哪些字段。目标字段的配置方式、案件内存在多个候选逻辑文件时如何确认目标，以及确认后如何分配写回，由 IDP 自行设计并在原型中明确；这部分不再作为客户待确认问题。

### 8. 共用的标准变量改了，什么时候需要重跑整案？

例如 A、B 两个照合组都用过 Data Mapping 生成的「性别」。操作员改了这个值，哪些结果要重新照合？［§4.6、§5.2］

#### 会议结论

v1.2 已区分两种情况：修改单据项目或表格单元格时，只对当前 item 重新标准化；案件标准字段、单据集合或案件整体判断相关输入改变时，以最新资料重新请求整案，并取消尚未结束的旧 Task。见 §4.1、§4.6。

## 配置接口

### 9. 配置页能否直接拿到每一列允许的照合方式？

现在 IDP 要组合判断 `inputRole` 和 `writable`。请主数据列表 API 直接返回角色名称、可以选的照合方式，以及能否作为主输入。IDP 直接画下拉选项，保存时继续调用整组校验。［§4.7、§4.9、§5.1］

```json
{
  "columns": [
    {"column": "DRUG.BRANDNAME", "configuration": {
      "roleLabel": "主输入，可回填",
      "allowedModes": ["INPUT", "OUTPUT", "INPUT_OUTPUT"],
      "canBePrimary": true
    }},
    {"column": "EXAMPLE.SUPPORTING_CODE", "configuration": {
      "roleLabel": "辅助输入，只读取",
      "allowedModes": ["INPUT"],
      "canBePrimary": false
    }},
    {"column": "DRUG.ATC", "configuration": {
      "roleLabel": "仅回填",
      "allowedModes": ["OUTPUT"],
      "canBePrimary": false
    }}
  ]
}
```

比如两个列都只有 `INPUT` 可选，一个可能是主输入，另一个只是辅助输入。需要额外知道角色，才能判断这个组有没有配置主输入。请客户确认能否提供上述三类列的真实样例。

#### 会议结论

v1.2 已在 `configuration` 中返回可直接用于界面的 `roleLabel`、`allowedModes` 和 `canBePrimary`。IDP 可用这些值显示角色、生成照合方式选项及判断能否作为主输入，无需自行组合规则。API 仍保留原始 `inputRole` 和 `writable` 字段；若要求从响应中删除这两个底层字段，v1.2 并未这样约定。本期按 `configuration` 实现。
