# 主数据照合 API｜规格与真实场景差异说明

## 已确认的接口规则

- 每个案件提交当时有效的全部账票。
- 单次请求最多 50 份，超过时使用相同 `caseNo` 拆分请求，并更改 `clientRequestId` 的请求序号。
- 请求进入 Zurich 队列。同一优先级按受理顺序处理，并发数量由 Zurich 控制。
- `priority=NORMAL` 为普通处理，`LOW` 在没有等待中的 `NORMAL` 时处理。
- 配置保存前调用 `groups/validate`。式样书没有要求独立试照合页面，IDP 不新增该页面。
- `items/standardize` 属于本期接口。单字段、多字段同时重新照合及并发控制都按本期范围实现。

## IDP 已定的批次处理

- 新文件到达时创建新的独立批次任务。
- 补件到达时同样创建新的独立批次任务。
- 每个独立批次任务的结果分别进入 OCR抽出确认。
- 同一业务批次因超过 50 份拆成多个 Zurich 任务时，由 IDP 保存多个 `taskId`，并合并展示这一批次的完整结果。
- 旧任务结果晚到时，只更新该任务自己的结果和待办，不修改其他任务。
- IDP 不另建案件级队列，沿用 Zurich 的同一优先级受理顺序。

## 结论

V1.1 已经回答排队、优先级、50 份以上拆分和配置校验的接口行为。批次任务划分与多个 `taskId` 的结果合并属于 IDP 内部处理。本次没有需要 Zurich 追加确认的问题。
