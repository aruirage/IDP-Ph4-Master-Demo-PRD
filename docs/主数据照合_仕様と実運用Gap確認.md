# 主データ照合 API｜仕様と実運用の差分説明

## 確定したインターフェースルール

- 各案件で、その時点の全有効帳票を送信する。
- 1リクエストは最大50件とする。超過時は同じ `caseNo` でリクエストを分割し、`clientRequestId` の連番を変更する。
- リクエストは Zurich の待ち行列に入る。同一優先度は受付順で処理され、並行数は Zurich 側が制御する。
- `priority=NORMAL` は通常処理、`LOW` は待機中の `NORMAL` がない場合に処理する。
- 設定保存前に `groups/validate` を呼び出す。独立した試照合画面は仕様書で必須とされていないため、IDP では追加しない。
- `items/standardize` は今回の対象インターフェースとする。単一項目、複数項目の同時再照合、同時実行制御を今回の範囲に含める。

## IDP の確定方式

- 新規書類の到着時は、新しい独立バッチタスクを作成する。
- 補件の到着時も、新しい独立バッチタスクを作成する。
- 各独立バッチタスクの結果は、それぞれ OCR 抽出確認へ進む。
- 1つの業務バッチが50件超で複数の Zurich タスクに分かれる場合、IDP が複数の `taskId` を保存し、1バッチ分の結果として統合表示する。
- 旧タスクの結果が遅れて返った場合、そのタスク自身の結果と確認待ちだけを更新し、他のタスクは変更しない。
- IDP は案件専用の待ち行列を追加せず、Zurich の同一優先度の受付順を利用する。

## 結論

V1.1 で待ち行列、優先度、50件超の分割、設定検証のインターフェース動作が明確になった。バッチタスクの分割と複数 `taskId` の統合表示は IDP 内部処理である。今回 Zurich 様へ追加確認する事項はない。
