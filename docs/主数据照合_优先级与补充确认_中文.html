以下问题集中在 API 行为、批次任务、补件、分片和并发。内部页面流程不再逐项确认。

1. 同一案件能否同时存在多个照合任务？任务并发
例：批次 1 还在处理中，批次 2 到达并新建任务。
IDP 方案：允许并行，新批次不取消旧任务。
2. 每个批次任务提交新文件，还是案件全部有效文件？请求范围
例：批次 2 只发领收书，还是发请求书＋诊断书＋领收书。
IDP 方案：按式样书发送案件全部有效文件。
3. 补件是否作为新的批次任务，并重新提交有效文件？补件
例：请求书、诊断书之后收到本人确认书。
IDP 方案：补件新增任务，提交当时全部有效文件。
4. 旧任务晚到时，是否只更新自己的任务结果？任务结果
例：任务 2 完成后，任务 1 才返回并更新任务 1 自己的结果。
IDP 方案：任务结果独立，不覆盖其他任务；案件汇总重新计算。
5. 多字段重新照合时，`items/standardize` 是否有并发上限？重新照合
例：同时修改金融机构和伤病名，产生两个请求。
IDP 方案：同一组一次请求，不同组分别请求；按确认的上限控制并行。
6. 超过 50 份文件拆成多个请求后，如何合并成一份案件结果？分片
例：60 份文件拆成 2 个请求，其中一个失败。
IDP 方案：全部请求成功后合并；任一失败时暂不合并，先重试或修正。
7. 同一字段被多个组设为回填目标时，冲突应如何呈现？回填冲突
例：金融机构名同时是两个组的 OUTPUT 目标。
IDP 方案：保存时警告；运行时产生 WRITE_CONFLICT 并进入人工确认。
8. 本期是否启用 callback 完成通知？专用试照合页面是否必须？可选范围
例：callback 不启用时继续轮询；试照合不强制时仅保留 groups/validate。
IDP 方案：两项都先按可选处理，由 Zurich 明确是否必须。
内部已确定的事项不再要求 Zurich 确认；本页只保留会影响 API 行为和本期范围的问题。
